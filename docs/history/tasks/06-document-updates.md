# Задача 06 — при изменении документа заменять его, а не хранить рядом

Контекст: `docs/tasks/01…05`. Сейчас корпус собран одним проходом, дублей версий нет (проверено ревью). Но при следующем обходе сайтов устаревшие версии начнут попадать в ответы. Эта задача — до LLM-агента (задача 07): агент не должен уметь процитировать отменённое.

## Что сломается сейчас (найдено ревью)
1. `doc_id` файла = `file:<sha256>`. Изменился PDF по тому же URL → новый sha → **новый документ**, а `parsed/<старый-sha>.json` остаётся; чанкер и индексатор берут **обе** версии.
2. Страница/файл пропали с сайта → остаются в индексе навсегда.
3. Страницы: `pages_parsing` пишет по `url_key`, это уже замена — проверь, что старые чанки страницы удаляются, когда её текст изменился (новые `chunk_id` → старые должны уйти из `chunks` и `lines`).

## Что сделать
1. **Стабильный идентификатор документа — по источнику, а не по содержимому.** `doc_id` файла = `file:<url_key основного URL>` (как у страниц `page:<url_key>`); sha256 — атрибут версии (`documents.sha256`, `documents.version`, `documents.updated_at`). Файл, найденный по нескольким URL с одинаковым содержимым, — один документ (основной URL = первый найденный, остальные — в `sources`). Миграция текущих данных без потери эмбеддингов (кэш по `content_hash` это позволяет).
2. **Замена при изменении.** Новая версия файла по тому же URL → тот же `doc_id`: чанки и строки документа пересобираются, ушедшие `chunk_id`/`line_id` удаляются, неизменившиеся тексты берут эмбеддинги из кэша. Старая версия остаётся **только в истории** (`document_versions` в реестре), в `chunks`/`lines` её нет. В `documents` — `previous_sha256`, `updated_at` (пригодится для «было → стало»).
3. **Чанкер/индексатор берут только актуальную версию** каждого документа (по реестру), а не все `parsed/*.json` подряд. Устаревшие `parsed/<sha>.json` можно не удалять, но в индекс они не попадают.
4. **Удалённые источники.** 404/410 или ссылка не найдена краулером **два обхода подряд** → документ `removed` (дата), его чанки и строки удаляются из поиска. Одного сбоя сети мало.
5. **Одна команда обновления** `scripts/update.sh`: `crawler --resume` → `downloader --refresh` → `parsing` (только новое) → `pages_parsing` → `indexing` → короткий отчёт: сколько документов новых / заменённых / удалённых / без изменений, эмбеддингов reused / computed. Логи в `data/logs/update-<дата>/`.

## Довесок из ревью задачи 05 (сделать после пунктов 1–5)
6. **Короткие строки не выкидывать, а склеивать.** Сейчас строки короче 15 символов отбрасываются. По спецификации 05 их надо приклеивать к соседней строке того же блока (например, «Art. 5» + следующая строка, «tel.» + номер). Найди, где это происходит при построении `lines`, исправь, добавь тест.
7. **Почистить `eval/lines.yaml`.** Цифры 05 (line hit@5 30%) пока нельзя считать честными: в наборе есть мусор.
   - Убрать вопросы, у которых gold-строка — OCR-мусор (пример: line-14).
   - Убрать слишком общие вопросы без однозначного ответа (line-32, line-60).
   - Исправить перевод: «Buburuza» = «Божья коровка», не «Бабочка» (line-58).
   - Gold-строки на украинском — убрать или пометить `lang: uk` и не считать в метрике.
   - Правило для оставшихся: вопрос должен иметь ровно один ответ в одной конкретной строке.
   - Перезапусти `run_line_eval.py` и дай в отчёте две таблицы: до и после чистки. Цифры брать только из вывода скрипта.

## Тесты (обязательно)
- фикстура «v1 → v2 одного PDF по одному URL»: после индексации в `chunks`/`lines` только тексты v2, `doc_id` не изменился, в истории 2 версии;
- «текст не изменился» → 0 пересчитанных эмбеддингов;
- «документ пропал 1 раз» → остаётся; «2 раза подряд» → `removed`, чанков нет;
- страница изменилась → старые `chunk_id` удалены.
