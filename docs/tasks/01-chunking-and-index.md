# Задача 01 — чанкинг и поисковый индекс корпуса

Ты работаешь в монорепо `qwerty` — хакатон DeepTech GigaHack 2026 (Кишинёв, 25–27 сентября). Времени мало: нужен **работающий и проверяемый** результат, а не идеальный. Прочитай задачу целиком до того, как писать код.

## 1. Контекст продукта (коротко)

Мы строим AI-ассистента Примэрии Кишинэу. Он отвечает жителям и сотрудникам на **румынском и русском** только по корпусу публичных документов мэрии (сайты из Annex 1 челленджа). Требования жюри:
- каждый ответ цитирует **конкретный документ и фрагмент** («Decizia nr. 12/3 din 14.03.2023 → Anexa 1 → pct. 12»);
- если информации нет — система явно говорит «нет в корпусе»; если документы противоречат — показывает оба;
- навигация по сайтам мэрии (направить на нужную страницу / контакты отдела).

Архитектура: **офлайн-пайплайн** (Python, `offline_indexation/`) превращает сайты и файлы в индекс → **онлайн** (`backend/`, FastAPI) ищет по индексу и отвечает через LLM → **фронт** (`frontend/`, Next.js) — чат-виджет. Качество цитат целиком зависит от того, как ты нарежешь документы в этой задаче.

## 3. Что сделать

Код — в `offline_indexation/`, в стиле существующего (маленькие модули, CLI через `python -m <stage>`, docstring с примерами запуска наверху `__main__.py`, комментарии в коде на английском). Зависимости — через `uv add`.

### 3.0 Мелкий фикс
`ocrmac` — только macOS, на Linux `uv sync` падает. Сделай его платформенной зависимостью: `ocrmac; sys_platform == 'darwin'`.

### 3.1 Сохранить координаты блоков (правка `parsing/build.py`)
Для подсветки цитаты в просмотрщике нужен bbox. Добавь в каждый блок `bboxes: [{page, l, t, r, b, origin}]` из `item.prov` (у блока может быть несколько prov), плюс размеры страниц в `pages[]` (`width`, `height` из `doc.pages`). Подними `PARSER_VERSION` до `"2"`. Пересборка без OCR должна работать через существующий `--rebuild` (кэш `.docling.json`).

### 3.2 Парсинг HTML-страниц — новый этап `pages_parsing` (или `parsing/html.py` + флаг)
Сейчас в корпус попадают только файлы, а страницы сайтов (услуги, процедуры, контакты) — нет. Это главные ответы для жителей.
- Вход: строки `pages` со `status < 400` и `html_file`.
- Основной контент: `trafilatura` (без меню/футера), с сохранением структуры: заголовки h1–h4 с уровнями, абзацы, пункты списков, таблицы (`header` + `rows`, как у файлов).
- Выход: `data/parsed/pages/<id>.json` **в той же схеме блоков**, что у файлов, плюс `kind: "page"`, `url`, `site`, `category`, `title` (из `<title>`/h1), `lang` (из `pages.lang` или `detect_lang`), `alternates`.
- Шаблонный мусор: блок с одинаковым текстом на > 30% страниц одного сайта — выкидывай (меню/футеры, которые trafilatura пропустила). НО не выкидывай телефоны/email/адреса со страниц контактов — они нужны для навигации: блоки с контактами (регексы телефон `(\+373|0)\s?\d…`, email) пометь `has_contacts: true` и оставь.
- Статус парсинга страниц храни в реестре (новая таблица или колонки в `pages` через `ALTER TABLE … ADD COLUMN`, идемпотентно) — чтобы повторный запуск обрабатывал только новые/изменившиеся (по хешу HTML).
- Пустые страницы (< 200 символов основного текста) — помечай `empty`, в чанки не отдавай.

### 3.3 Юридическая структура (новый модуль, например `chunking/legal.py`)
Docling строит `section` только по распознанным заголовкам, а в решениях «Articolul 4», «pct. 12», «alin. (2)» часто обычные абзацы. Нужен второй путь — `legal_path`:
- регексы на начало блока (после `marker`), RO и RU:
  - RO: `Anexa (nr.) N`, `Capitolul I/II/…`, `Secțiunea N`, `Articolul N` / `Art. N`, `punctul N` / `pct. N` / нумерация вида `12.` `12.3.` в начале пункта, `alineatul (N)` / `alin. (N)`, `litera a)` / `lit. a)`;
  - RU: `Приложение (№) N`, `Глава N`, `Раздел N`, `Статья N` / `Ст. N`, `пункт N` / `п. N` / `12.` / `12.3.`, `часть (N)`, `подпункт a)`;
- поддерживай стек уровней (Anexa > Capitol > Secțiune > Articol > pct > alin > lit), новый уровень выталкивает глубже лежащие;
- **осторожно с ложными срабатываниями**: «în conformitate cu art. 14 din Legea nr. 436/2006» в середине предложения — это ссылка, а не начало статьи. Срабатывай только на начало блока;
- покрой **pytest-тестами** на фикстурах: минимум 15 кейсов, включая RO, RU, ложные ссылки, нумерацию `5.2.`, Anexa внутри решения.

### 3.4 Чанкинг (новый этап `chunking`)
Вход: `data/parsed/*.json` (файлы) и `data/parsed/pages/*.json` (страницы). Выход: таблица `chunks` в индексе (см. 3.5) и `data/chunks/<doc_id>.jsonl` для отладки.

Правила:
- граница чанка — смена `legal_path` на уровне пункта/статьи или смена `section` (заголовка);
- соседние короткие блоки одного родителя склеиваются до ~1500 символов; блок/юнит > ~2500 символов режется по абзацам/предложениям с перекрытием ~200 символов;
- **таблицы**: отдельные чанки; строки группами до ~1500 символов, **заголовок таблицы повторяется в каждом чанке**; маленькая таблица — целиком;
- **никогда не склеивай** блоки из разных документов, разных `legal_path`-статей, разных языков;
- поля чанка:
  - `chunk_id` — стабильный: `sha1(doc_id + first_block_id + last_block_id + parser_version)`;
  - `doc_id` (`file:<sha256>` или `page:<url_key>`), `kind` (`file` | `page`);
  - `text` — **дословный** текст блоков (из него будут цитаты, ничего не перефразировать и не добавлять);
  - `embed_text` — `"{title}\n{citation_label}\n{text}"` (контекстный префикс для эмбеддинга);
  - `citation_label` — человекочитаемо: `"Decizia nr. 12/3 din 2023-03-14 › Anexa nr. 1 › pct. 12"`; для страниц — `"{title} › {h2}"`;
  - `section[]`, `legal_path[]`, `block_ids[]`, `pages[]`, `bboxes[]`, `lang`, `char_count`, `content_hash` (sha1 от `text`);
  - `has_contacts`, `is_table`;
  - копия метаданных документа: `title`, `doc_type`, `number`, `date`, `category`, `site`, `url` (основной URL файла/страницы), `found_on` (страница, где найден файл — первая из `sources`).

### 3.5 Индекс (новый этап `indexing`) — Postgres + pgvector
- `docker-compose.yml` в корне репо: `pgvector/pgvector:pg17`, порт 5432, volume, креды через `.env` (добавь `.env.example`). Схему создаёт код (`CREATE … IF NOT EXISTS`), расширения `vector` и `unaccent`.
- Таблицы: `documents` (по одной строке на `doc_id` с метаданными) и `chunks` (все поля выше + `embedding vector(1024)` + `tsv tsvector`).
- Эмбеддинги: `BAAI/bge-m3` (dense, 1024, нормализованные) через `sentence-transformers`; на Mac использовать `mps`, если доступно, иначе CPU; батчи. **Инкрементально:** если `content_hash` уже есть с эмбеддингом — не пересчитывать. Удалять чанки документов, которых больше нет в выходе чанкинга.
- Full-text: `to_tsvector('simple', unaccent(embed_text))` (румынского стеммера в Postgres нет). Индексы: HNSW (cosine) по `embedding`, GIN по `tsv`, btree по `doc_id`, `category`, `lang`.
- Проверь, что `torch`/`sentence-transformers` ставятся на Python 3.14 (проект требует `>=3.14`). Если нет — остановись и опиши варианты в отчёте, не меняй версию Python молча.

### 3.6 CLI поиска для проверки — `python -m indexing.search`
```bash
uv run python -m indexing.search "cât costă autorizația de construire" -k 5
uv run python -m indexing.search "как вывезти крупногабаритный мусор" -k 5 --lang ru
```
Гибрид: вектор top-40 + FTS top-40 (`websearch_to_tsquery('simple', unaccent(q))`) → слияние RRF (k=60) → top-k. Печатать: ранг, RRF-скор, ранги в обоих списках, `citation_label`, `url`, язык, первые 200 символов `text`. Реранкер НЕ нужен (это следующая задача).

## 4. Чего НЕ делать
- не трогать `backend/` и `frontend/`;
- не делать LLM-классификацию тем, связи между решениями, извлечение фактов — это следующие задачи;
- не ломать существующие CLI (`crawler`, `downloader`, `parsing`) и не менять существующие таблицы реестра деструктивно — только добавлять;
- не включать `--ignore-robots`;
- не коммитить `data/`, модели, `.env`.
