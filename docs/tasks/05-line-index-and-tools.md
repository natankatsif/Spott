# Задача 05 — индекс строк, дерево документа, инструменты агента, честный eval

Прочитай `docs/tasks/04-retrieval-service.md`, свой отчёт по 04 в `offline_indexation/REPORT.md` и код `packages/retrieval`, `backend/app/main.py`. Человек у компьютера. **Mac — 8 ГБ RAM:** в одном процессе держим только bge-m3 (fp16, ~1.2 ГБ); реранкер по умолчанию выключен.

## Зачем
Сейчас ищем по чанкам: факт из одной строки внутри длинного чанка «растворяется» в его векторе, а цитировать мы хотим **конкретную строку**. Дальше (задача 06) ответы будет давать агент на GPT, который ходит по корпусу инструментами `search / grep / toc / open`, цитирует строки по их `line_id` и честно говорит «нет в корпусе». В этой задаче делаем всё, что нужно агенту, **кроме самого LLM-цикла**.

LLM проекта — **OpenAI GPT по API**. Ключ лежит в корневом `.env` (`OPENAI_API_KEY`), модель — `OPENAI_MODEL` (выбери актуальную быструю дешёвую модель по документации OpenAI, значение — в `.env.example` без ключа). В этой задаче GPT нужен только для генерации eval.

## 1. Строки как единица поиска и цитирования
- В **чанкере** (там есть блоки) добавь каждому чанку `lines: [{idx, text, block_id}]`: деление по `\n`; строка > 400 символов — по предложениям; строки < 25 символов (`a)`, `1.`) склеиваются со следующей; строка таблицы = одна строка с заголовками колонок в `embed_text`. Текст строк — **дословный** (конкатенация строк = `chunk.text` с точностью до пробелов/переносов; тест на это).
- Таблица `lines`: `line_id` (стабильный `sha1(chunk_id:idx)`), `chunk_id` FK (CASCADE), `doc_id`, `idx`, `text`, `embed_text` (`"{title} › {citation_label}\n{text}"`), `lang`, `block_id`, `page`, `bboxes` (bbox блока), `embedding vector(1024)`, `tsv` (по языку, как у чанков). Индексы: HNSW по `embedding`, GIN по `tsv`, **GIN `pg_trgm` по `text`** (для `grep`), btree `(chunk_id, idx)`.
- Индексатор пишет строки теми же батчами и тем же кэшем по `content_hash` (хеш текста строки). Замерь время и число строк.

## 2. Поиск по строкам + чанкам
- `retrieve()` ищет **по строкам** (вектор + FTS) и **по чанкам** (вектор), сливает на уровне чанка: скор чанка = взвешенный RRF по его лучшей строке и по самому чанку. Каждый результат несёт `matched_lines: [{line_id, idx, text, score}]` (1–3 лучшие строки).
- Кросс-языковые вопросы FTS не находит (RU-вопрос ↔ RO-текст) и шумит в RRF — сделай **веса RRF** (`W_VECTOR`, `W_FTS`, `W_LINE`) в конфиге и подбери по eval (п.4), а не на глаз.

## 3. Дерево документа и инструменты (без LLM)
`retrieval/tools.py` — чистые функции поверх пула + JSON-схемы для OpenAI function calling в одном месте (`TOOL_SCHEMAS`):
- `search(query, lang?, site?, k=8)` → чанки с `matched_lines`, `citation_label`, `doc_id`, `url`.
- `grep(pattern, doc_id?, site?, limit=20)` → строки с точным вхождением (`ILIKE` через `pg_trgm`; без регулярок от пользователя в SQL — экранировать).
- `toc(doc_id)` → оглавление: узлы по `section` + `legal_path` в порядке документа (добавь в `chunks` колонку `ord` = номер первого блока), у узла `node_id`, заголовок, число строк.
- `open(doc_id, node_id | chunk_id, max_lines=60)` → строки узла с `line_id` и `idx`, в порядке документа.
- Лимиты размера ответа каждого инструмента (символы), чтобы агент не утонул.
- HTTP: `POST /api/tools/{search,grep,toc,open}` для отладки и для фронта. Тесты: без БД — схемы/экранирование/сборка дерева из списка чанков; с БД — помечены `@pytest.mark.db`, в CI по умолчанию пропускаются.

## 4. Eval, который меряет то, что нам важно
- `offline_indexation/eval/gen_line_eval.py` (GPT): выбери ~80 случайных строк (стратифицировано по сайтам, без шаблонных/коротких/OCR-мусорных), для каждой GPT пишет вопрос жителя, ответ на который — **именно эта строка**: половина RO, половина RU (**кросс-языковые**), без копирования фраз (отбрось, если > 50% значимых слов вопроса есть в строке). Плюс 12 правдоподобных вопросов про мэрию, которых **нет** в корпусе (проверь `grep` + `search`, что ответа нет). Сохрани в `eval/lines.yaml` с `gold_line_id`, `gold_chunk_id`. Отметь в отчёте, что 10 случайных вопросов человек должен проверить глазами (выведи их списком).
- Метрики: **line hit@1/@5**, chunk hit@5, MRR; режимы: чанки-вектор (как сейчас), строки-вектор, строки+чанки, + варианты весов FTS. Для «нет в корпусе» — распределение лучших скоров (понадобится порогу в 06, но решать будет LLM).
- Старый `search_smoke.yaml` тоже прогони в новой схеме для сравнения.
- Итог: выбранные веса по умолчанию и почему (цифрами).
