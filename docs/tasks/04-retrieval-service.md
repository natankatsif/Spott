# Задача 04 — быстрый сервис поиска в бэкенде + честный eval

Прочитай `docs/tasks/01…03`, `offline_indexation/REPORT.md` и последние коммиты (`git log -5`). В коммите `d4c3e94` код индексации и поиска почищен: единый UPSERT, строки как dict, модели в fp16 загружаются один раз, у реранкера `max_length=512`, флаги `--sites`/`--limit`/`--rerank`. **Не откатывай это.** Человек у компьютера: Docker и модели можно.

## Зачем эта задача
Офлайн (краулинг, OCR, эмбеддинги корпуса) может идти долго, это нормально. **Ответ на вопрос должен быть быстрым.** Сейчас каждый CLI-запуск заново грузит две модели по ~2 ГБ, отсюда минуты ожидания. В сервере модели грузятся **один раз при старте**, и запрос стоит миллисекунды на поиск плюс ~0.5–1 с на реранкер. Цель задачи — доказать это цифрами.

## Правила кода (проверю)
- `uv run ruff check .` чистый (конфиг уже в `offline_indexation/pyproject.toml`; такой же добавь в новые пакеты);
- никакого копипаста SQL/логики между модулями; строки БД — `dict_row`, не `row[11]`;
- чистые функции покрыты тестами без БД и моделей; `uv run pytest` зелёный во всех пакетах;
- цифры в отчётах — только выводом скриптов.

## Что сделать
1. **Индекс.** `docker compose up -d`, `uv run python -m indexing` по всему текущему корпусу (2269 чанков; с fp16 на MPS это должны быть минуты). В отчёт: устройство, время, чанков/сек, `SELECT count(*) … WHERE embedding IS NULL` = 0. Если чанков/сек < 20 на MPS — выясни почему (своп? `sysctl hw.memsize`, Activity Monitor), напиши и остановись.
2. **Переписать `eval/search_smoke.yaml`** (прошлая версия слабая):
   - 8 RO + 8 RU, из них ≥ 4 кросс-язычных (RU-вопрос → RO-документ);
   - вопросы как у жителя, **без копирования фраз из документа**; только по темам, реально присутствующим в индексе (проверь по `data/chunks`);
   - ожидание: `site` + список допустимых `doc_ids`; ключевые слова — только доп. проверка;
   - 4 «нет в корпусе» — **правдоподобные вопросы про мэрию**, ответа на которые в индексе нет (проверь поиском по `data/chunks`), а не пицца/телепортация;
   - прогон `uv run python -m indexing.eval_smoke` (4 режима). В `REPORT.md` — таблица hit@1 / hit@5 / MRR / латентность и распределение скоров реранкера у позитивных vs негативных.
3. **Пакет `retrieval` (uv workspace).** Корневой `pyproject.toml` с `[tool.uv.workspace] members = ["offline_indexation", "backend", "packages/retrieval"]`. Перенеси в `packages/retrieval/src/retrieval/`: `db.py` (подключение + схема), `embeddings.py`, `rerank.py`, `search.py` (+ `build_fts_query`, `deduplicate_results`, `rrf_fuse`). Зависимости пакета минимальные: `psycopg[binary,pool]`, `pgvector`, `numpy`, `sentence-transformers`, `python-dotenv`. `offline_indexation` и `backend` зависят от `retrieval` как workspace-пакета; `offline_indexation/indexing` импортирует оттуда, дубликатов не остаётся. Тесты переносятся вместе с кодом.
4. **Бэкенд: `POST /api/search`.**
   - FastAPI `lifespan`: пул соединений (`psycopg_pool.ConnectionPool`), загрузка bge-m3 и реранкера, **прогревочный запрос**; `GET /health` отдаёт устройство, загружены ли модели, число чанков в индексе.
   - Запрос: `{query, lang?, k=8, rerank=true}` → `{results: [{chunk_id, doc_id, citation_label, text, url, found_on, site, lang, page, parent_legal_path, rerank_score, vec_rank, fts_rank}], timings_ms: {embed, vector_sql, fts_sql, rerank, total}}`.
   - Векторный и полнотекстовый запросы — **параллельно** (два соединения из пула в `run_in_threadpool`/`anyio.to_thread`); модели вызываются в потоке, чтобы не блокировать event loop.
   - Кандидатов в реранкер — 30, конфиг в одном месте (`retrieval/config.py`: `TOP_CANDIDATES`, `RERANK_TOP_K`, `NOT_FOUND_THRESHOLD`).
   - `NOT_FOUND_THRESHOLD` — из распределения скоров шага 2 (середина между худшим позитивным и лучшим негативным; если они пересекаются — напиши, насколько, и возьми значение с минимумом ошибок). Если лучший скор ниже порога — в ответе `not_found: true`.
5. **Бенчмарк латентности** — `backend/scripts/bench_search.py`: 16 вопросов из eval × 3 прогона против поднятого сервера, p50/p95 по каждому этапу `timings_ms`, с реранкером и без. **Цели на Mac:** поиск без реранкера p95 < 300 мс, с реранкером p95 < 1500 мс. Не укладываемся — предложи варианты с цифрами (top-20 вместо 30; `Qwen3-Reranker-0.6B`; реранкер по API) и **остановись** — это решение команды.
6. `README.md`: как поднять бэкенд с поиском, пример `curl`.

## Поправка (важно)
`retrieval/rerank.py`: `MAX_LENGTH = 512` обрезает хвост у ~12% чанков (длиннее ~1500 символов) — реранкер не видит последние строки, а там может быть ответ. Поставь `MAX_LENGTH = 1024` и в бенчмарке (п.5) сравни латентность 512 vs 1024; если 1024 не укладывается в цель — не возвращай 512, а сообщи цифры.
