# 3. Бэкенд и API

FastAPI (`backend/app/main.py`), админка (`admin.py`), пробелы (`gaps.py`), быстрые вопросы
(`suggestions.py`), превью источников (`preview.py`).

## S1. Лимиты входа и вопросов обходятся подменой `X-Forwarded-For` — **высокая**

**Где:** `admin.py: login` и `main.py: client_id`:

```python
forwarded.split(",")[0].strip() or request.client.host
```

Первое значение `X-Forwarded-For` пишет **клиент**; прокси (Caddy, cloudflared) лишь дописывают адрес в
конец. Отправляя каждый раз новый `X-Forwarded-For`, можно:
- перебирать пароль админки без ограничения «5 попыток в минуту»;
- обходить лимит вопросов и тратить деньги на модель (защита QR-стенда).

Кроме того, `RateLimiter.hits` — словарь без очистки: каждый выдуманный адрес остаётся в памяти навсегда.

**Решение:** верить `X-Forwarded-For` только когда соединение пришло от прокси во внутренней сети
(Caddy и cloudflared подключаются к API из сети Docker, то есть с приватного адреса), и брать из него
**последний** адрес — тот, который дописал наш прокси. Запрос напрямую на опубликованный порт 8000 с
публичного адреса считается по своему адресу, заголовок игнорируется. Пустые очереди из словаря удалять.

**Сделано:** да (`errors.client_address()`, общий для входа и вопросов; тесты).

## B1. Отключённый источник продолжает участвовать в ответах — **средняя**

**Где:** `admin.py: patch_source(enabled=False)` меняет только флаг; документы сайта остаются в индексе, а
поиск (`retrieval`) о флаге не знает. Админ ожидает, что «Отключить» убирает сайт из ответов.

**Предложение:** исключать в поиске сайты отключённых источников (фильтр `site <> ALL(disabled)` в
запросах `retrieval/search.py`, список кэшировать на несколько секунд) или удалять документы при
отключении. Не сделано ночью: затрагивает все четыре SQL-запроса поиска и требует решения, что делать при
повторном включении (переиндексация или хранение). В интерфейсе стоит подписать, что отключение
останавливает только обновления.

## B2. Добавление ссылки в существующий источник ставит обработку, даже если идёт другая — **низкая**

**Где:** `admin.py: add_source`, ветка `existing`. Обычный запуск проверяет «ещё выполняется», эта ветка
нет. Worker всё равно выполняет обработки по одной, так что вреда мало, просто в очереди две работы по
одному сайту.

## S2. Добавление источника запрашивает любой адрес — **низкая**

`probe()` и `robots_allowed()` делают запрос по ссылке, которую вставил админ, в том числе на
`localhost`/внутренние адреса. Раз это делает только вошедший админ, риск низкий; при открытии админки
большему числу людей стоит отсекать приватные адреса.

## G1. Первое открытие «Вопросов без ответа» ждёт модель — **низкая**

`PgGaps.list` синхронно сортирует новые вопросы маленькой моделью (по 40 за вызов). Когда накопилось много
новых вопросов, первое открытие страницы занимает несколько секунд. Решения хранятся, так что следующие
открытия быстрые. Можно вынести сортировку в фон после записи ответа (`on_done`), но при текущих объёмах
не нужно.

## G2. Каждое открытие списка заново считает эмбеддинги всех вопросов — **средняя (скорость)**

`PgGaps.list` группирует все вопросы без ответа, и `group()` каждый раз прогоняет через bge-m3 **все** их
тексты. С новым счётчиком в меню админки это происходило бы на каждой странице.
**Решение:** хранить векторы вопросов в памяти между вызовами (новые вопросы досчитываются), а два
одновременных списка выполнять по очереди, чтобы новые вопросы не сортировались моделью дважды.
**Сделано:** да (`CachedEmbed`, блокировка в `PgGaps.list`; тест).

## Хорошо сделано

- Токен админки подписан HMAC, смена пароля обнуляет все сессии, сравнение через `compare_digest`.
- Превью показывает только проиндексированные документы (нет открытого прокси), CSP с nonce, песочница.
- Вопросы на публичной «стене» маскируются (телефоны, почта, длинные числа).
- Запись ответа и оценки никогда не ломает сам ответ (`try/except` с логом).
