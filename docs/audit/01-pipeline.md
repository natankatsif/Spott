# 1. Пайплайн: обход → скачивание → разбор → индексация → обработки

Как устроено: обработка из админки (`jobs`) берётся worker'ом (`offline_indexation/worker`), который по
очереди запускает этапы для одного сайта (`worker/core.py: plan`):

```
crawler --sites X          → registry.sqlite: pages, documents, document_sources; data/crawl/X/html/*.html
downloader --sites X       → data/raw/<sha>…, files, documents.status/sha256/etag
parsing                    → data/parsed/<sha>.json (Docling, OCR)
pages_parsing --sites X    → data/parsed/pages/<hash>.json (блоки, без повторяющихся меню/подвалов)
indexing --sites X         → Postgres: documents, chunks, lines (+ эмбеддинги bge-m3, повторное использование по хэшу)
```

Идея хорошая: каждый этап идемпотентный, можно прервать и продолжить, эмбеддинги не пересчитываются для
неизменного текста, прогресс и отмена через файл. Ниже то, что работает не так, как задумано.

---

## I1. Удалённые документы и страницы навсегда остаются в индексе — **высокая**

**Где:** `offline_indexation/indexing/__main__.py`, `main()`:

```python
is_full_corpus = not (args.from_jsonl or args.sites or args.limit)
if args.clean_orphans and is_full_corpus:
    orphans_removed = indexer.clean_orphaned_documents(set(by_doc))
```

Worker всегда запускает `indexing --sites <сайт>` (и для «всех источников» тоже передаёт список сайтов),
поэтому `is_full_corpus` в админке **никогда** не истинно, и документы, которых больше нет среди
действующих, не удаляются. Кроме того, если у сайта не осталось ни одного действующего документа,
`main()` выходит раньше («No chunks match the filters») и тоже ничего не чистит.

**Последствия:** PDF, убранный с сайта (registry: `removed`), страница, ставшая 404 или пустой, отключённая
версия документа продолжают находиться поиском и цитироваться в ответах. Это прямо противоречит задаче
«не выдумывать и опираться на актуальные документы».

**Решение:** при частичном прогоне по сайтам удалять из индекса документы *этих сайтов*, которых нет среди
действующих: `DELETE FROM documents WHERE site = ANY(%s) AND doc_id <> ALL(%s)`; делать это и тогда, когда
у сайта не осталось ни одного документа. Прогон с `--limit` или `--from-jsonl` по-прежнему ничего не чистит.

**Сделано:** да (`clean_orphaned_documents(active, sites=…)`, тесты в `tests/test_indexer_sql.py`).

## D1. Временная ошибка сайта или первый 404 выкидывают документ из индекса — **высокая**

**Где:** `downloader/core.py: Downloader.download` → `registry.mark_checked(key, "failed", …)`;
`common/registry.py: record_download_missing` ставит `status = 'missing'` после первого 404;
`active_file_documents()` берёт только `status = 'downloaded'`.

При обновлении (`--refresh`) уже скачанный документ перезапрашивается. Если сайт в этот момент ответил 5xx,
оборвал соединение или истёк таймаут, документ становится `failed`, и при следующей индексации его нет среди
действующих. Первый же 404 делает его `missing` — тоже не действующий, хотя по замыслу
(`consecutive_missing >= 2 → removed`) документ должен удаляться только после двух промахов подряд.
Вместе с исправлением I1 это превратилось бы в удаление хорошего документа из-за одного сбоя сайта.

**Решение:** документ, у которого уже есть скачанная версия, при сбое сохраняет статус `downloaded`
(записываются только `http_status`, `error`, `checked_at`), а при первом 404 — тоже остаётся `downloaded`
с `consecutive_missing = 1`; `removed` — со второго 404 подряд или по результатам обхода.

**Сделано:** да (`Registry.mark_checked`, `record_download_missing`; тесты в `tests/test_versioning.py`).

## D2. Обновление не перепроверяет «пропавшие» и «сломанные» документы — **средняя**

**Где:** `downloader/__main__.py: download_all` — при `--refresh` берутся статусы `discovered` и
`downloaded`; `worker/core.py: plan` не передаёт `--retry-failed`.

Документ со статусом `missing` больше никогда не запрашивается, поэтому не может ни вернуться, ни
окончательно стать `removed`. `failed` из админки тоже никогда не повторяется.

**Решение:** при обновлении перепроверять `missing` и `failed` тоже.

**Сделано:** да (обновление = `--refresh --retry-failed`, `missing` добавлен к статусам обновления).

## W1. Обработка, прерванная перезапуском worker'а, «идёт» вечно — **высокая**

**Где:** `worker/__main__.py`. `claim()` ставит `running`; если процесс убит (перезапуск контейнера, сон
ноутбука, OOM на OCR), строка остаётся `running`. `start_job` в админке отвечает 409 «ещё выполняется»,
источник показывает «Идёт», прогресс не двигается. Отменить её тоже нельзя: отмена `running` только
ставит флаг, который читает worker.

**Решение:** worker один на машину (так написано в модуле), значит при старте всё, что `running`, —
осиротевшее: пометить `failed` с понятной ошибкой («прервано перезапуском обработчика»).

**Сделано:** да (`PgJobStore.recover_interrupted()` при запуске; тест).

## C1. Каждый обход заново разбирает все страницы — **средняя, осознанный компромисс**

**Где:** `common/registry.py: upsert_page` — `INSERT OR REPLACE` удаляет строку и вставляет новую,
поэтому `parse_status`, `html_hash`, `parsed_at` сбрасываются; `pages_to_parse` берёт `NULL` как
«ещё не разобрано».

После обхода разбираются все страницы сайта, даже не изменившиеся. На текущих объёмах (до 150 страниц на
сайт) это секунды; плюс в том, что определение повторяющихся меню и подвалов видит весь сайт (см. C3).
Индексация всё равно не пересчитывает эмбеддинги неизменного текста.

**Решение (не делалось):** хранить хэш HTML в `pages` и ставить `pending` только при изменении, а
частоты блоков для удаления меню брать по всем страницам сайта. Пока объёмы маленькие, выигрыша почти нет.

## C3. Добавленная ссылка на раздел сайта индексируется вместе с меню и подвалом — **средняя**

**Где:** `parsing/html.py: parse_site_pages`. Повторяющиеся блоки (меню, подвал) определяются по частоте
среди страниц *текущего прогона* и только если их не меньше трёх. Когда админ добавляет ссылку на раздел
уже известного сайта, обходятся 1–2 страницы, частоты не считаются, и меню со всеми ссылками попадает в
чанки. Такие чанки потом всплывают в поиске.

**Решение:** считать частоты по всем разобранным страницам сайта (HTML уже лежит на диске), а разбирать
только нужные.

**Сделано:** да (`pages_parsing` передаёт в разбор все страницы сайта как контекст для частот).

## IX1. Индексация одного сайта заново режет на чанки весь корпус — **средняя (скорость)**

**Где:** `indexing/__main__.py: main` вызывает `chunk_all()` по всем действующим документам и только потом
фильтрует `--sites`. Обработка маленького сайта ждёт чанкинга всех остальных.

**Решение:** резать только документы нужных сайтов; устаревшие `.jsonl` удалять только при полном прогоне.

**Сделано:** да.

## C2. Префикс пути сравнивается как строка — **низкая**

`crawler/site.py`: `path.startswith(self.site.path_prefix)` — префикс `/ro/servicii` подходит и к
`/ro/servicii-noi`. Лучше сравнивать по сегментам (`p == prefix or p.startswith(prefix + "/")`).
**Сделано:** да.

## Другое, без исправления

- **Автоматического обновления нет** — только кнопка «Обновить» у источника (исправлена ранее: теперь
  полный обход). Предложение: ночной запуск `refresh` для всех включённых сайтов (решение за владельцем:
  это нагрузка на сайты мэрии).
- **`.doc` (старый Word)** распознаётся как документ, но Docling его не читает → `unsupported`. Можно
  конвертировать через LibreOffice, если такие файлы встречаются.
- **Тело страницы > 15 МБ** обрезается молча (`MAX_BODY_BYTES`). Редкость, но стоит писать в лог.
