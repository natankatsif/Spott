# План: автоматическое обновление сайтов

Цель: ассистент узнаёт об изменениях на сайтах мэрии в течение суток, не нагружая их и не завися от того,
нажал ли кто-то «Обновить».

## Что есть у сайтов (проверено 27.09.2026 на 39 включённых сайтах)

| Сигнал изменений | Сайтов | Примеры |
|---|---|---|
| `sitemap.xml` с датами (`<lastmod>`) | 11 | autosalubritate.md, amt-centru.md, ciocana.md, invest.chisinau.md |
| `sitemap.xml` без дат | 11 | help.chisinau.md, dgams.md, rtec.md, visit.chisinau.md |
| WordPress API (`/wp-json/wp/v2/…?modified_after=`) | 18 | help.chisinau.md, suburbii.chisinau.md, detscentru.md |
| Только заголовки `Last-Modified` / `ETag` на страницах | 5 | mobilitatechisinau.md, egradinita.md, agsv.md |
| Ничего | 10 | **proiecte.chisinau.md, dgaurf.md, acc.md**, chisinauedu.dgets.md, liftservice.md |

WordPress и sitemap часто есть у одного сайта сразу. Важно, что самые содержательные сайты (dgaurf,
proiecte) не дают вообще никаких сигналов, поэтому запасной путь обязателен, а не на всякий случай.

## Три режима проверки

### 1. Ежедневная лёгкая проверка «что изменилось» (ночью, для каждого включённого сайта)

Для каждого сайта берётся лучший доступный способ по порядку:

1. **WordPress API.** Запросы `pages`, `posts` и `media` с `modified_after=<последняя проверка>`.
   В ответе сразу приходят изменённые страницы и новые файлы (PDF). Это 3–6 запросов на сайт.
2. **Sitemap с датами.** Скачивается `sitemap.xml` (и вложенные), из него берутся адреса с `lastmod`
   новее последней проверки и адреса, которых мы ещё не знаем.
3. **Sitemap без дат.** Только новые адреса. Изменения существующих страниц ловит шаг 5 или недельный обход.
4. **Условный запрос.** Для страниц, где сервер отдаёт `ETag`/`Last-Modified`, повторный запрос с
   `If-None-Match`/`If-Modified-Since`; ответ 304 означает «не менялось», и тело не передаётся.
5. **Отпечаток ключевых страниц** (для сайтов без всего вышеперечисленного). Главная и «списочные»
   страницы первого уровня (новости, документы, решения, объявления — те, откуда обход обычно находит
   больше всего документов). Сравнивается хэш *основного текста* (без меню, дат в шапке, счётчиков и
   токенов), а не всего HTML, иначе каждая страница «меняется» каждый день. Если отпечаток изменился,
   обходится эта ветка сайта на глубину 1–2.

Найденные новые и изменённые адреса проходят обычный путь: скачивание → разбор → индексация только их.
Способ, который сработал для сайта, запоминается в `sources`, чтобы не пробовать всё каждый раз. Раз в
неделю способ определяется заново: сайт мог переехать на другой движок.

**Нагрузка:** от 1–6 запросов на сайт (WordPress, sitemap) до примерно 10–30 запросов (отпечатки) плюс
скачивание только изменившегося. Соблюдаются `robots.txt`, `Crawl-delay` и пауза между запросами.

### 2. Еженедельный полный обход

Обычное «Обновить» для всех включённых сайтов, по одному, ночью в выходной. Он нужен, чтобы:
- найти то, чего нет ни в sitemap, ни в API (страницы вне WordPress, файлы в произвольных папках);
- убрать пропавшее: страницы, до которых обход не дошёл, и документы, не найденные два раза подряд (это
  уже работает в `audit-fixes`);
- перепроверить все PDF условным запросом.

### 3. Внеочередная проверка по сигналу

Сайт ставится в очередь на лёгкую проверку (режим 1), если:
- при открытии цитаты живая страница уже не содержит процитированный текст (превью «не нашёл это место»);
- человек нажал 👎 и выбрал «Устарело»;
- админ нажал «Обновить».

Ограничение: не чаще раза в 6 часов на сайт, чтобы серия дизлайков не превращалась в DoS. Сигналы копятся
и видны в админке («2 сигнала об устаревании»).

## Где это живёт

- **Планировщик** — внутри worker'а, который уже работает постоянно: раз в минуту он смотрит, какие сайты
  пора проверить (`sources.next_check_at`), и ставит обработку вида `check` или `refresh`. Отдельный cron
  не нужен, всё видно в «Обработке».
- **Новый вид обработки `check`**: этапы «найти изменения → скачать → разобрать → проиндексировать
  только изменённое». Прогресс и отмена такие же, как у остальных.
- **Таблица `sources`**: `check_method` (wp / sitemap / conditional / fingerprint), `last_checked_at`,
  `next_check_at`, `fingerprints` (JSON: адрес → хэш текста), `stale_signals`.
- **Админка**: у источника видны «проверено N часов назад, способ: WordPress» и сигналы; в настройках
  выключатель «Автообновление» и время ночного окна.

## Крайние случаи

- **Sitemap есть, но устаревший** (генерируется плагином, который сломан): если три проверки подряд по
  sitemap ничего не нашли, а недельный обход нашёл изменения, способ понижается до отпечатков.
- **WordPress API закрыт или отдаёт 401/403** — переход к следующему способу, без повторных попыток.
- **Сайт недоступен ночью** — проверка переносится на +2 часа, после трёх неудач подряд на следующий день;
  документы и страницы при этом не удаляются (это уже работает в `audit-fixes`).
- **Сайт внезапно «изменился» целиком** (редизайн): отпечатки всех страниц разные. Лёгкая проверка не
  пытается обработать всё, а ставит полный обход.
- **robots.txt запретил обход** — источник помечается «Запрещён robots.txt», проверки прекращаются.

## Порядок работы

1. Лёгкая проверка: WordPress и sitemap (покрывают 24 из 39 сайтов), вид обработки `check`, планировщик
   в worker'е, поля в `sources`.
2. Условные запросы и отпечатки для остальных сайтов (dgaurf, proiecte, acc…).
3. Еженедельный полный обход через тот же планировщик.
4. Сигналы от превью и дизлайков, ограничение 6 часов.
5. Админка: «проверено когда и как», сигналы, выключатель автообновления.

Каждый шаг отдельным коммитом, с тестами на фейковом сайте (фиктивные sitemap, ответы WordPress, 304).
